# Share record label-access typechecking between projection and mutation

Field projection and `%atomic_loc` share `solve_Pexp_field` — instantiate the label, unify the record with the label's record type, and (since #5461) call `update_labels` to compute the use-site representation — but `Pexp_setfield` still had its own copy of the same logic. This PR moves that block into `type_label_access` so there's one copy, resolving an XXX comment from #5461 asking why it couldn't be shared. `solve_Pexp_field` is deleted, and setfield no longer needs its fresh sort-jkinded `ty_record` variable, since `update_labels` imposes representability instead.

This also answers a second XXX, which wondered why `update_labels` had to be called inside the local level ("weird errors happen if we don't"), so that comment is deleted. Both XXXs come down to the same mechanism: the block's unifications lower the levels of generalized nodes in `record.exp_type` and `ty_arg`, and it takes a level exit's structure re-generalization to re-raise them — run `update_labels` outside the level and the lowering persists, so under `-principal` the projection result reads as non-principal and e.g. stops mode crossing (caught by `tests/typing-local/crossing.ml`). The historical "principality issues" with sharing were the same thing one step removed: the level's `~post` used to re-generalize only `ty_arg`, which was fine for projection, but setfield reads `record.exp_type` again to type the assigned value, so its disambiguation spuriously warned under `-principal` (warning 18, caught by `tests/typing-misc/disambiguate_principality.ml`). Since "Automatic generalize" (#12946), exiting the level re-generalizes the structure of every node lowered to it — `record.exp_type` included — so sharing no longer needs any extra fix.

One behavior change, captured by the new `tests/typing-layouts/label_access_checking_order.ml` (promoted before and after the change): setfield now checks the record's representability before typing the assigned value, so when both would error, the layout error is reported instead of the value's. For `%atomic_loc`, which already required the record's fields to be representable, only the jkind history changes: the error's reason line becomes "it's the type of a field being assigned a value" rather than "it's the type of a field in a record being projected from".

The new test also exposed a pre-existing bug in the `Jkind_sort` error reporter: unlike its sibling branches, it printed types without `Printtyp.wrap_printing_env ~error:true`, so idents it printed polluted the persistent naming context and a later error mentioning a distinct ident of the same name printed it with a stamp (`a/2` instead of `a`). Fixed by adding the wrapper.
