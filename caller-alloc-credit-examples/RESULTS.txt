Crediting the caller's allocations in speculative inlining decisions
====================================================================

Flag: -flambda2-speculative-inlining-credit-caller-allocations (off by
default, not part of -flambda2-inline-2026).

What it does
------------

When a Let binds an allocation (a block, or a set of closures with a single
closure) to a variable that occurs exactly once in the rest of the function
body, the allocation's cost is remembered.  When a call is judged after
speculative inlining, each argument that is such a variable and that the
simplified inlined body no longer mentions is counted as removed: its size
plus the bonus for a removed allocation is added to the call-site credit.
The occurrence counts come from the Let itself (they are stored in the term
when it is built), so no extra pass is needed.

Examples (this directory), compiled on arm64 with

  ocamlopt.opt -O3 -flambda2-inline-2026 [flag] -inlining-report -S -c exN.ml

  ex    description                       2026              2026 + flag
  ----  --------------------------------  ----------------  ----------------
  ex0   let f (x, y) = ... ; f (z, z)     not inlined 0.93  not inlined 0.93
        (tupled function)                 no tuple at all   no tuple at all
  ex1   let f p = let x, y = p in ...     not inlined 0.91  inlined 0.59
        g z = f (z, z)                    1 allocation      0 allocations
  ex2   as ex1, tuple also stored in a    not inlined 0.89  not inlined 0.89
        ref after the call
  ex3   as ex1, f stores the tuple in a   not inlined 0.86  not inlined 0.86
        ref
  ex4   closure (fun n -> n + z) passed   not inlined 0.83  inlined 0.67
        to f, applied once in f           6 functions       4 functions
                                          1 allocation      0 allocations

The numbers are the ratio of the adjusted size after speculation to the
original size (maximum 0.8).

ex0 is the example as first stated.  [let f (x, y) = ...] is a "tupled"
function: a direct call with a syntactic tuple passes the components as
separate arguments, so no tuple is ever built, inlined or not.  ex1 takes the
tuple as a single parameter and takes it apart inside.

ex1 in detail (arm64 sizes):

  original size                 46
  size after speculation        44 (4 prims removed: the projections)
  call-site credit              2  without the flag
                                17 with it: 2 + 11 (the block allocation)
                                   + 4 (bonus for a removed allocation)
  adjusted size                 42 -> 27
  ratio                         0.913 -> 0.587

ex2: the tuple is used twice, so it is never recorded.  ex3: f keeps the
tuple, so the inlined body still mentions it and nothing is credited.

ex4: the closure's cost (allocation plus the out-of-line code of its
function, 18) and the bonus (4) give a credit of 22 on top of the usual 2.
After inlining, the closure's function is inlined at its single call and its
code deleted, so both the allocation and a function disappear.

Sanity check on typing/ (deps from _build/main, arm64, -O3, 2026 model)

  unit      text bytes         call sites inlined  credited  flipped
  --------  -----------------  ------------------  --------  -------
  typecore  693076 -> 696148   4284 -> 4304        sum 2351  5
            (+0.4%)
  ctype     494440 -> 503836   2902 -> 2944        sum 1267  22
            (+1.9%)
  env       277489 -> 277713   1350 -> 1351        sum 163   0
            (+0.1%)

Flipped decisions are real instances of the pattern: [Types.backtrack snap]
where [snap] is a tuple built by the inlined [Btype.snapshot ()] (credit 5
-> 20, ratio 0.89 -> 0.75), and [Misc.protect_refs [R (pool_stack, pool)]
f] in [Btype.with_new_pool] inlined into ctype.ml:211, where the closure [f]
is applied once (credit 4 -> 67, ratio 0.85 -> 0.24; ctype goes from 1892 to
1870 functions).

Stats keys (with -dinlining-stats): speculation.caller_allocation_credited
(number of decisions given a credit) and speculation.caller_allocation_credit
(sum of the credits).

Callees that match on an option (or record) argument
----------------------------------------------------

Same compilation as above.  "big" is a 20-line chunk of integer arithmetic
(about 120 instructions on arm64), "medium" a 9-line one (about 50).

  ex    description                               2026                2026 + flag
  ----  ----------------------------------------  ------------------  ------------------
  ex5   None -> big | Some x -> x + 1             inlined 0.00        inlined -0.11
        called with Some z                        0 allocations       0 allocations
  ex6   None -> 0 | Some x -> big                 not inlined 0.94    not inlined 0.83
        called with Some z
  ex6b  None -> 0 | Some x -> medium              not inlined 0.87    inlined 0.64
        called with Some z                        1 allocation        0 allocations
  ex7   as ex6, Some arm also passes o to an      not inlined 0.92    not inlined 0.92
        external function
  ex8   as ex6, called with                       not inlined 0.97    not inlined 0.97
        (if z > 0 then Some z else None)
  ex9   two option parameters, both taken apart,  not inlined 0.89    inlined 0.69
        called with (Some z) (Some (z + 1))       1 allocation        0 allocations
  ex10  immutable record { count; name }, arm     not inlined 0.86    inlined 0.74
        taken reads r.count; called with          1 allocation        0 allocations
        { count = z; name = "g" } true
  ex11  as ex10 with mutable count, read and      not inlined 0.87    not inlined 0.87
        written in the arm taken

Reading
-------

ex5: when the argument rules out the big arm, the speculation never visits
it, the inlined body is three instructions, and the call is inlined without
any help; the [Some] disappears in both configurations.  The credit only
pushes the adjusted size below zero (ratio -0.11), which is harmless.

ex6 and ex6b: when the big arm is the one taken, inlining saves only the
match and the call (6 instructions on arm64) plus, with the flag, the [Some]
(size 10, bonus 4).  Against a 0.8 maximum this flips functions up to about
(6 + 2 + 14) / 0.2 = 110 instructions: ex6b at 61 flips (0.87 -> 0.64), ex6
at 131 does not (0.94 -> 0.83).

ex7, ex8 and ex11 are the three ways the credit does not apply: the inlined
body still mentions the argument (ex7 passes it on, ex11 reads and writes a
mutable field), or the value flowing into the call is not a single
allocation bound by a Let (ex8 joins two branches).

ex9 and ex10: credits add up over several arguments (2 x 14 in ex9), and an
immutable record behaves like a tuple (ex10, credit 13 + 4).

Merging the return continuation's handler into the inlined body
================================================================

Flag: -flambda2-speculative-inlining-merge-return-continuation (off by
default, not part of -flambda2-inline-2026).

What it does
------------

When a call's return continuation kr is bound by a Let_cont in the current
function body and used exactly once (per the count stored in the Let_cont),
every inlining of that call, speculative or not, produces

  let_cont kr retval... = <handler of kr> in <inlined body>

instead of just the inlined body, shadowing kr.  The handler is thus
simplified with what is known about the returned values at each return
point (the parameters of kr can be unboxed, matches on them resolved, dead
arms dropped), and the original handler, now without any use, is deleted.
The speculative inlining decision sees the simplified handler as part of
the inlined body; in exchange the size of the original handler (measured
by Code_size_report on the unsimplified handler) is added to the call-site
credit, and so to the budget.  Only inside function bodies: at the unit
toplevel every binding's continuation is single-use, and merging them nests
the rest of the module into inlined bodies, which loses the static
allocation of toplevel closures.

During a speculation the merged handler may jump to continuations defined
outside of the speculated expression (the function's return continuation,
join points).  The upwards environment of the speculation is given every
continuation in scope at the call site, with the arities recorded at their
Let_conts, and the data flow analysis treats a jump to a continuation it
does not know like a jump to the return continuation (its arguments are
required and escape).

Examples (rx*.ml; "medium" is a 9-line chunk of integer arithmetic, about
50 instructions), compiled on arm64 with

  ocamlopt.opt -O3 -flambda2-inline-2026 [flag] -inlining-report -S -c rxN.ml

  ex    description                               2026                2026 + flag
  ----  ----------------------------------------  ------------------  ---------------------
  rx1   f returns Some/None, g matches at once    not inlined 0.91    inlined 0.66
                                                  g: 24 instr, call   g: 54 instr, no call,
                                                                      no Some allocated
  rx2   as rx1 but kr shared by two calls to f    not inlined 0.91    not inlined 0.91
  rx3   f returns a pair, g takes it apart        not inlined 0.90    inlined 0.65
                                                  g: 23 instr         g: 49 instr, no pair
  rx4   f returns a float, g adds to it           not inlined 0.90    inlined 0.39
                                                  g: 31 instr         g: 62 instr, 5 boxes
                                                                      fewer in the body
  rx5   f returns Some on every path, g has a     not inlined 0.92    inlined (credit 151)
        big None arm                              g: 115 instr        g: 50 instr: the None
                                                                      arm is gone

rx1 in detail: the handler (match, size 13) is credited, so the call-site
credit goes from 3 to 16; after speculation the merged handler has its
parameter unboxed, one allocation and seven primitives are removed, and the
ratio falls from 0.905 to 0.662.  rx5: the big arm of the handler is
unreachable once the handler sees that f only returns Some, so the credit
of 151 (its size) far exceeds what is left.

rmain.ml links rx1-rx5 and prints their results: identical under 2026,
2026 + merge, and 2026 + merge + the allocation credit.  Likewise 46 of the
programs under testsuite/tests/basic* print the same output under 2026 and
2026 + both flags.

Sanity check on typing/ (deps from _build/main, arm64, -O3, 2026 model)
-----------------------------------------------------------------------

  unit      text bytes                 call sites inlined  handlers merged
  --------  -------------------------  ------------------  ---------------
  env       277489 -> 279254 (+0.6%)   1350 -> 1333        515
  ctype     494440 -> 500664 (+1.3%)   2902 -> 2705        695
  typecore  693076 -> 680147 (-1.9%)   4284 -> 3962        976

Compile times are unchanged within noise.  Fewer call sites are inlined
with the flag: the speculated expression now contains the handler, whose
own simplification (notably the small calls inlined inside it) can cost
more than the size measured on the unsimplified handler, and the budget of
150 is reached sooner (typecore: 1092 of 2133 speculations aborted before,
947 of 1679 after).  The credit is an estimate of the handler's size before
simplification; nothing better is available at decision time, since the
handler is normally simplified after the body.

Stats keys: speculation.return_continuation_merged (decisions with a merged
handler) and speculation.return_continuation_credit (sum of the credits).
